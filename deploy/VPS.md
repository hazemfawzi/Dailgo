# نشر Node.js على VPS عن طريق SSH

هذه حزمة تطبيق جاهزة للتجربة على VPS، وليست إثباتًا أن النشر تم. القوالب تفترض Linux مع systemd وNginx؛ أمثلة الأوامر تناسب Ubuntu/Debian. يجب ضبطها حسب نظام السيرفر والدومين الفعليين. لم تُنفّذ أوامر SSH على أي سيرفر بعد.

## المتطلبات والحدود

- Node.js 24 مثبت على مستوى النظام ومتاح في `/usr/bin/node`. تحقق بـ `/usr/bin/node --version` وبإمكانية تحميل `node:sqlite`.
- التطبيق يخدم الواجهة وAPI من نفس أصل HTTPS. استخدم دومينًا فرعيًا أو جذر دومين؛ مسار فرعي مثل `/assistant-app/` غير مدعوم في هذه الحزمة.
- SQLite تدعم هذا المنتج ذي المستخدم الواحد. توجد نسخة مستقلة على السيرفر؛ نقل النسخ من المتصفح وإليه يدوي، بمعاينة وتأكيد، وليس مزامنة تلقائية أو نظامًا متعدد المستخدمين.
- لا توجد اعتمادات npm مطلوبة لتشغيل الحزمة المجهزة. لا ترفع `node_modules` أو قاعدة بيانات جهاز التطوير.
- AI والربط بتطبيقات خارجية غير مفعّلين. ملفات البيانات والنسخ الاحتياطية غير مشفرة على القرص، ويجب أن تبقى خاصة بالمستخدم التشغيلي.

## 1. قبل الرفع

احصل على عنوان VPS، اسم مستخدم SSH، نظام التشغيل وإصداره، والدومين. لا تضع كلمات المرور أو المفتاح الخاص في المحادثة. تحقق من بصمة مضيف SSH مع جهة الاستضافة عند أول اتصال؛ لا تتجاوز فحص المضيف.

وجّه DNS للدومين إلى السيرفر. حضّر Node 24 وNginx وأداة شهادات TLS المناسبة للتوزيعة. اترك منفذ Node داخليًا على `127.0.0.1:8787`، ولا تعرضه للإنترنت. لا تغيّر قواعد SSH أو جدار الحماية دون الحفاظ على إمكانية دخولك.

## 2. رفع نسخة مستقلة

استخدم `scp` أو SFTP لرفع ملف الحزمة إلى حساب SSH، ثم تحقق من SHA-256 المنشور بجوارها. بعد فك الضغط، تحقق من الملفات:

```sh
sha256sum -c SHA256SUMS
```

داخل `/srv/personal-os/releases/`، أنشئ مجلدًا جديدًا لكل إصدار وانقل إليه محتويات الحزمة. لا تكتب فوق مجلد الإصدار السابق. سيشير الرابط `/srv/personal-os/current` إلى الإصدار المختار. يجب أن تكون ملفات الإصدار مملوكة للمشرف وقابلة للقراءة لمستخدم الخدمة، دون السماح له بتعديل كود التطبيق.

## 3. حساب النظام والإعدادات

أنشئ مستخدم خدمة مخصصًا باسم `personal-os` بدون دخول تفاعلي، ومجلد بيانات خاصًا `/var/lib/personal-os` مملوكًا له بصلاحيات `0700`. هذه خطوات إدارة تُنفّذ مرة واحدة وفق توزيعتك، ولا تستخدم حساب root لتشغيل Node.

انسخ `deploy/production.env.example` إلى `/etc/personal-os.env` واجعله مملوكًا لـroot بصلاحيات `0600`. عدّل:

- `APP_ORIGIN`: أصل الدومين HTTPS فقط، بدون `/` في النهاية.
- `PERSONAL_OS_DB`: مسار مطلق خاص خارج مجلدات الإصدارات والويب.
- `PERSONAL_OS_SETUP_TOKEN`: قيمة عشوائية سرية بطول 32 حرفًا على الأقل، وليست النص الافتراضي.

يمكن توليد رمز خاص على السيرفر باستخدام `openssl rand -hex 32`، ثم وضعه في ملف الإعدادات. لا تضع الرمز في رابط أو في متغيرات Vite، ولا ترفعه ضمن الحزمة. إزالته من الإعدادات بعد إنشاء الحساب يعطّل تهيئة أول حساب عند غياب قاعدة البيانات.

انسخ `deploy/personal-os.service` إلى مجلد وحدات systemd المناسب. راجع مسار Node والكود، ثم:

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now personal-os
sudo systemctl status personal-os
```

الخدمة مقيدة بالقراءة على النظام، والكتابة على مجلد البيانات الخاص فقط. الإيقاف يعالج الاتصالات ثم يغلق SQLite.

## 4. Nginx وHTTPS

ابدأ بقالب `nginx-bootstrap.conf.example` بعد استبدال الدومين، وأنشئ مجلد تحدي ACME `/var/www/personal-os-acme`. لا تستبدل إعدادات مواقع أخرى على السيرفر. افحص `nginx -t` قبل إعادة التحميل.

أصدر شهادة TLS للدومين باستخدام أداة الشهادات التي اخترتها ومسار webroot المذكور. بعد وجود الشهادة، استخدم `nginx-https.conf.example` مع تعديل الدومين ومسارات الشهادة. افحص الإعدادات وأعد تحميل Nginx. تأكد من تجديد الشهادة تلقائيًا.

القالب يحافظ على Host الصحيح ويستبدل ترويسات عنوان العميل والبروتوكول قبل تمرير الطلب إلى Node. وضع الإنتاج يرفض Host غير الموافق للدومين، أو اتصالًا لا يعلن الوكيل الموثوق أنه HTTPS، أو كتابة من Origin مختلف. لا تُستخدم ترويسات وكيل من مصدر عام مباشر.

راجع المصادر الرسمية قبل تكييف القوالب: [Nginx proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)، و[systemd service execution settings](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html).

## 5. التحقق وإنشاء حسابك

- افتح `https://YOUR_DOMAIN/api/health` وتحقق من `status: production` وأن AI والربط غير مفعّلين.
- افتح التطبيق والبيانات/النسخ الاحتياطي، ثم افحص السيرفر. أنشئ اسم المستخدم وكلمة المرور بنفسك باستخدام رمز التهيئة الخاص.
- تحقق من تسجيل الدخول والخروج وتغيير كلمة المرور، ومن أن Cookies تحمل `Secure` و`HttpOnly` و`SameSite=Strict`.
- صدّر نسخة احتياطية من بيانات المتصفح القديمة أولًا. افتح النسخة المنشورة واستورد النسخة بمراجعة، ثم احفظها على السيرفر بعد المعاينة. كل دومين/منفذ له تخزين متصفح مستقل.
- اختبر فشل استبدال نسخة قديمة، والتراجع، والملفات، وفتح `/assistant/actions` مباشرة بعد التحديث.
- اختبر التثبيت وفتح التطبيق دون إنترنت بعد اكتمال التخزين مرة. API لا يُخزّن بواسطة service worker.

## 6. النسخ الاحتياطي والاستعادة

انسخ خدمتي النسخ الاحتياطي والمؤقت من `deploy/`، ثم:

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now personal-os-backup.timer
sudo systemctl start personal-os-backup.service
sudo systemctl status personal-os-backup.service
```

النسخ يستخدم SQLite backup API بدل نسخ ملف قاعدة مفتوح؛ النتيجة تُفحص بـ`quick_check` وتُحفظ بصلاحيات `0600` في `/var/lib/personal-os/backups`. النسخ الموجودة على نفس القرص ليست حماية من فقد السيرفر. حضّر نقلًا مشفرًا إلى مكان مستقل وراقب المساحة. لا يوجد حذف تلقائي للنسخ القديمة.

لاستعادة قاعدة، أوقف خدمة التطبيق، احتفظ بالنسخة الحالية وملفات WAL المرتبطة بها، وتحقق من نسخة الاستعادة، ثم استبدل القاعدة من خلال إجراء إداري مُراجع بصلاحيات المستخدم الصحيحة. لا تنسخ قاعدة فوق عملية Node تعمل. ألغِ الجلسات القديمة أو أعد تعيين كلمة المرور إداريًا بعد الاستعادة، ثم شغّل الخدمة وافحص البيانات.

## 7. استعادة الدخول إداريًا

من داخل إصدار التطبيق وعلى السيرفر فقط، يمكن تشغيل `server/maintenance.mjs reset-password` ببيئة الإنتاج ومسار قاعدة البيانات. يستقبل كلمة المرور الجديدة من stdin محمي، ويرفض وضعها كوسيطة أو إدخالها على شاشة مكشوفة. يُفضّل تمريرها من أداة مثل `systemd-ask-password` إلى مهمة systemd مؤقتة تعمل كمستخدم الخدمة مع `EnvironmentFile=/etc/personal-os.env`. العملية تلغي جميع الجلسات. لا تضع كلمة المرور في shell history أو ملف نشر.

## 8. تحديث الإصدار والرجوع

أنشئ نسخة احتياطية ناجحة قبل التحديث. ارفع إصدارًا جديدًا إلى مجلد منفصل، وافحص البصمات. بدّل رابط `current` ذريًا إلى الإصدار الجديد ثم أعد تشغيل الخدمة وافحص HTTPS والصحة والبيانات. عند فشل الإصدار، أعد الرابط للإصدار السابق وأعد التشغيل؛ لا تُرجع قاعدة البيانات تلقائيًا مع الكود.

لا تشغّل ترحيلات مدمرة على قاعدة قائمة دون خطة استعادة مجرّبة. راقب `journalctl -u personal-os` ومساحة القرص ونجاح النسخ والشهادات. لا تسجّل كلمات المرور أو رموز الجلسات أو محتوى البيانات في سجلات الطلبات.

## حالة التحقق

اختبارات API المحلية تغطي فصل الإنتاج، Origin وHost وHTTPS الوكيل، رمز التهيئة، الجلسات الآمنة، تغيير كلمة المرور، وفحص النسخة الاحتياطية. لم يُنفّذ نشر على VPS فعلي، أو فحص `nginx -t` وsystemd على نظام الاستضافة، أو اختبار TLS/متصفح حقيقي بعد. يلزم عنوان السيرفر والدومين ونظامه لإتمام هذه الخطوات.
